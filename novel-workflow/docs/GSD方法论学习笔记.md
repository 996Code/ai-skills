## 一、GSD核心理念

### 1. 渐进式精炼（Progressive Refinement）

GSD不做"顶层分解固定规格"，而是通过提问、讨论、研究逐步**发现**要做什么。

```
模糊想法 → 提问挖掘(spec) → 灰区讨论(discuss) → 研究规划(plan) → 执行(execute) → 验证(verify)
```

每一阶段增加精确度，纠正假设。

### 2. 思维伙伴哲学（Thinking Partner）

> "用户=创始人/愿景家。AI=建造者。"

- AI不应该问用户关于技术模式、架构风险的问题——那是AI的职责
- AI只问关于愿景、偏好和会影响结果的实施选择
- AI是思考伙伴，不是面试官

### 3. WHAT与HOW严格分离

- **spec-phase** 锁定"做什么和为什么"（需求、边界、验收标准）
- **discuss-phase** 锁定"怎么做"（实施决策、灰区）
- **plan-phase** 锁定"构建顺序和任务"（可执行提示词）
- **execute-phase** 锁定"干活"（并行子代理执行）

## 二、GSD阶段详解

### spec-phase（规格阶段）— 苏格拉底访谈循环

**核心**：通过多轮访谈，把模糊需求变成可验证的规格文档。

**量化模糊度模型**（4维度，0.0-1.0）：

| 维度 | 权重 | 最低要求 |
|------|------|---------|
| 目标清晰度 | 35% | 0.75 |
| 边界清晰度 | 25% | 0.70 |
| 约束清晰度 | 20% | 0.65 |
| 验收标准 | 20% | 0.70 |

**模糊度 = 1.0 - 加权平均**。门槛：模糊度 ≤ 0.20 且所有维度≥最低要求。

**访谈视角轮换**：
1. 研究者（round 1-2）：扎根现实
2. 简化者（round 2）：找到最小可行范围
3. 边界守护者（round 3）：锁定边界
4. 失败分析师（round 4）：找推翻需求的边缘案例
5. 闭环者（round 5-6）：锁定所有未决区域

**关键规则**：每个需求必须有现状、目标态、验收标准。边界是明确列表。验收标准是通关/失败检查项。模糊需求直接拒绝。

### discuss-phase（讨论阶段）— 灰区决策提取

**核心**：提取下游代理需要的实施决策。识别"灰区"——用户在乎的、可能走多条路的实施选择。

**流程**：
1. 加载阶段上下文，检查阻塞反模式
2. 加载先验上下文（PROJECT.md、REQUIREMENTS.md、STATE.md等）
3. 交叉引用待办事项与阶段范围
4. 轻量代码扫描（~10%上下文），找可复用资产
5. 分析阶段：识别领域边界、检查先验决策、生成灰区
6. 展示灰区：用户选择讨论哪些（3-4个具体区域）
7. 逐区讨论：模式依赖的交互方式
8. 写CONTEXT.md：记录领域、决策、规范引用、代码上下文、具体细节、延后想法
9. 检查点持久化：每个区域后增量保存

**范围护栏**：讨论只澄清"怎么实施已确定范围"，绝不讨论"是否加新能力"。范围蔓延捕获为延后想法，不在当前阶段执行。

### plan-phase（规划阶段）— 研究→规划→验证循环

**核心**：最复杂的工作流，编排研究→规划→验证，最多3轮修订循环。

**关键步骤**：
1. 封闭阶段门控（防止重规划已完成工作）
2. 解析参数（MVP模式、TDD模式、研究标志等）
3. 加载CONTEXT.md
4. 处理研究——派生gsd-phase-researcher子代理
5. 创建验证策略
6. 派生gsd-planner子代理创建PLAN.md
7. 派生gsd-plan-checker子代理——修订循环（最多3轮）
8. 后规划缺口检查

### execute-phase（执行阶段）— 波浪式并行执行

**核心**：按依赖波浪分组计划，波浪间串行，波浪内并行。

- 波浪分组——有依赖关系的计划先完成
- 并行执行——git worktree隔离并发计划
- 波内重叠检测——共享文件时强制串行
- 检查点心跳——防超时断连

## 三、GSD关键技巧（适配小说创作的灵感）

### 追问技术（Questioning）

- **追线索**：追逐用户强调的，不走检查单
- **挑战模糊词**："好是什么意思？""用户是谁？""简单是什么？"
- **让抽象变具体**："带我走一遍使用流程"
- **揭示动机**："什么促使你这样想？""如果这个存在你会怎么做？"

**反模式**：不走检查单、不说官话、不审讯式提问、不催促、不提前设限、不问用户技术经验

### 领域探测（Domain Probes）

结构化的领域知识表——将用户提到的术语映射到专家级追问。挑选2-3个最相关的，不当检查单走。

### 灰区识别（Gray Areas）

根据领域类型（SEE/CALL/RUN/READ/ORGANIZE）自动生成关键决策点，每个标注代码上下文和先验决策。

### 特定性测试（Specificity Test）

> "另一个Claude实例能否无需追问就执行这个任务？如果不能，就加更多细节。"

### 计划反模式（Planner Anti-Patterns）

禁止语言：
- "v1"、"简化版"、"先硬编码"、"未来增强"
- 模糊任务如"加认证"
- 反射式SUMMARY链
- 验证疲劳

如果阶段太复杂，推荐拆分阶段，而不是偷偷缩减范围。

### 多模式适配

- `--auto`：AI选推荐方案，最少交互
- `--chain`：自动推进讨论→规划→执行
- `--power`：精炼单轮讨论
- `--batch`：每轮2-5个问题分组
- `--analyze`：每个问题前展示权衡表

## 四、GSD → 小说创作的适配映射

| GSD概念 | 小说创作适配 |
|---------|-------------|
| spec-phase 苏格拉底访谈 | 探矿阶段：需求挖掘，创意成熟度量化 |
| discuss-phase 灰区讨论 | 探矿阶段：灰区决策（视角/节奏/结局/基调/结构） |
| plan-phase 规划 | 谋篇阶段：三级大纲（总纲→卷纲→章纲） |
| execute-phase 执行 | 执笔阶段：分段生成+迭代精修 |
| verify 验证 | 审校阶段：一致性检查+文风统一 |
| 模糊度量化 | 创意成熟度量化（核心冲突35%+角色动机25%+世界观边界20%+读者预期20%） |
| 反模式防护 | 禁止凑合写、角色跑偏、伏笔遗忘、范围偷减 |
| 上下文传承 | Bible文档跨阶段自动传承 |
| 灰区识别 | 关键创作决策点识别 |
| 特定性测试 | 大纲章节能否无需追问就写出来？ |
